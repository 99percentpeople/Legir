# PDFium 架构检查与表单导出修复（2026-10-15）

检查基线：`engine/pdfium` 的 `b65cf9c`。结论：当前架构适合继续迭代，
无需再替换引擎。单实例、原生读写和应用编辑模型的边界已经建立。检查发现的
表单导出外观问题已按实际外观状态修复；结构上仍应收紧模块依赖、任务接口和
测试入口，避免继续把职责堆进大型文件。以下区分原检查证据与后续修复。

## 当前职责与保留约束

| 层                                                | 所有权和职责                                                                                                         |
| ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| React / editor stores                             | 草稿、历史、页序和交互状态；PDFium 不再承担另一份可编辑 UI 状态。                                                    |
| `pdfService/index.ts` / `pdfWorkerService.ts`     | 主线程客户端、消息协议、取消和资源传递。原始字节通过 `documentOwners` 找到对应 Worker。                              |
| `pdf-render.worker.ts` / `DocumentSession`        | 每个文档标签一个常驻原生 PDF；串行访问、事务回滚、导入源、渲染和保存。导入选择期间允许临时 donor，完成或取消后释放。 |
| `documentPipeline.ts` / parsers / exporters / lib | Legir 的表单、批注、嵌套回复、页身份、导入和导出保留策略。                                                           |
| `@legir/pdfium/authoring`                         | 同一原生 xref 上的懒视图，以及字体、表单、图像和外观生成；不再加载另一套 PDF 解析器。                                |
| `@legir/pdfium` / native bridge                   | PDF 解析、密码、对象图、graft、事务、渲染、增量与完整写出。SDK 不依赖 React、Zustand 或应用 Worker。                 |

已核对的关键实现：

- [DocumentSession](../src/services/pdfService/engine/documentSession.ts) 在同一个原生对象上执行草稿事务，`finally` 中回滚。导入源以页库和对象映射保留；单实例约束是“每个打开的文档”，不是整个应用只能打开一个 PDF。
- [Worker](../src/workers/pdf-render.worker.ts) 用串行任务锁保护文档，读者渲染优先于预览。主线程不保存第二份解析后的 xref。
- [editingDocument](../src/services/pdfService/engine/editingDocument.ts) 借用 authoring 视图，分块调用原生保存任务并检查取消；完整输出和增量后缀由同一个原生 writer 产生。
- [扫描页渲染器](../packages/pdfium/src/scan.ts) 是受能力判断保护的快路径；复杂页面保留原生回退，通用 Canvas-plan API 仍是实验能力。
- [构建产物校验](../packages/pdfium/scripts/verify-artifacts.mjs) 对照固定源码、补丁、工具链与 WASM 哈希，避免源代码和已提交二进制不一致。

## 发现与处理

### 已修复：未编辑表单的外观一致性

统一 corpus 工具跑通了打开、绘制、导入和两种保存，但独立 Poppler 校验
拒绝了新建表单样本的两个输出：单独导出 3 页、合并导出 6 页。页数、字段值、
文字、结构全部一致，9 个页面比较的像素均超过现有差异门槛。样本是三个
400×500 点页面，各带一个 Helvetica 文本框（200×30 点），导入源采用不同字段名。

[documentPipeline.ts 的保存收尾](../src/services/pdfService/documentPipeline.ts)
原先在存在普通表单、没有未展平自由文本时写入 `/NeedAppearances true`。这次样本
的字段 `/AP`、`/DA` 和矩形没有改变，但该标志从缺省变为 true，Poppler 随后
重新生成外观，文字位置出现变化。诊断副本只将它改为 false，9 个页面就都与
原文件逐像素一致。

使用清理前 `32d3d8c` 的浏览器构建重跑，输出字段及全部 9 个渲染哈希与当前
构建完全一致。因此这是已有的导出策略问题，不是脚本清理引入的回归。

后续修复将决策移入 [form-appearances.ts](../src/services/pdfService/lib/form-appearances.ts)，
在页选择和展平完成后，仅检查实际保留的页面控件：

- 完整的普通外观和当前按钮状态外观不再被无条件标记为需要重建。
- 缺失、非法、仍为 dirty 或生成失败的外观保留阅读器回退。生成失败即使没有
  字段值修改，也会标记为 dirty。
- 源文件已请求重建时，仅在所有可见、非签名控件成功生成外观后清除请求；
  仅修改元数据或部分字段不会误清除其他旧外观的修复请求。
- 可编辑 XFA 保留源策略和数据；打印展平仍关闭重建。隐藏控件和原生签名
  不触发无意义的外观重建。
- 检查借用现有 native view，不解码外观流、不打开另一个 PDF，并复用保存任务
  的取消检查点。每个字段仍只批量生成一次外观，没有增加全表单反复扫描。

[formAppearances 测试](../tests/pdf/formAppearances.test.ts) 覆盖完整/增量保存、
旧外观、缺失状态、失败回退、孤立/隐藏/签名控件、选页、XFA 和取消。
既有 [exportForms 测试](../tests/pdf/exportForms.test.ts) 的 CJK 和 XFA 预期继续保留。
严格像素验证门槛未作修改。

复现输出和前后校验保留在本机 `/tmp/legir-pdfium-cleanup/`，没有把临时 PDF、
PNG 和日志加入仓库。当前正式真实语料没有可填写表单，所以此前真实语料的
像素通过结果不能覆盖这个问题。

## 页面旋转后印章方向修复（2026-10-15）

旧版在旋转整个页面、保存后重新打开时，印章解析没有计入源页 `/Rotate`，
90°/270° 后的外接框被当成未旋转图片的宽高；导出又对导入印章跳过页旋转补偿。
现已统一新建和导入印章的坐标约定，保留局部宽高，并在读写两端应用互逆旋转。
从 AP 提取的路径 SVG 使用原生外观语义；实际渲染页裁剪仍是 baked 外观，避免
重复旋转。路径提取遇到文字绘制时转入完整预设/渲染回退，防止重存时丢失印章文字。

- 在既有 `stampDisplayMode.test.ts` 新增 33 项回归，覆盖 JPEG、源 SVG、无私有
  标记的 AP 路径 SVG、文字预设，90°/180°/270°、原页已有旋转、印章自身角度、
  CropBox 和 UserUnit，以及 baked 图像不重复旋转。强制重建外观后的原生像素
  与保存前一致。完整应用 101 个文件、863 项测试，SDK 9 个文件、71 项测试通过。
- ESLint、应用和营销站 TypeScript、WASM 产物检查、生产 PWA 构建通过。
- 真实 Chromium 对照复现旧版 90° 后图片方向/宽高错误；修复版完成三类印章各
  90°/180°/270° 的九组页面旋转、保存、重新打开流程。重开后局部尺寸和旋转角度
  均正确，彩色非对称印章的截图方向一致，每次文档活动 Worker 为 1，无页面脚本异常。
- 九个浏览器输出经 qpdf（pikepdf）语法检查通过；独立 Poppler 渲染均与只修改
  原文件页旋转的参考文件逐像素一致。未新增 PDF 运行时实例或修改 WASM；本次未

## 其他批注和表单的旋转往返检查（2026-10-15）

继续检查全部可编辑批注与五类表单控件，确认并修复以下问题：

- 缺省 widget `/MK/R` 或 FreeText 旋转信息时，导入漏算源页角度；转回 0° 时
  widget 导出又没有清掉旧角度。现统一把缺省值视为 PDF 空间的 0°，并保留页旋转。
- 自由文本用显示宽高除以 PDF 宽高估算缩放，在 90°/270° 时混用了两组轴。
  现直接采用 viewport 变换的缩放量，保留局部文字框比例。
- 图片签名的方向与容纳尺寸使用了屏幕角度；现转换为 PDF 角度后计算尺寸和位置，
  覆盖 contain/fill 与页面、签名自身旋转组合。
- 云线矩形在恢复局部坐标之前扣除外扩边距；云多边形判断顶点是否已旋转时忽略
  云线和笔画边距，可能再次旋转顶点。现分别调整计算顺序和候选范围。
- 矩形/椭圆在自身 45° 时无法仅靠外接框恢复宽高。现使用已有 AP BBox 的比例，
  没有读取第二份 PDF 或改变保留原始外观的导出路径。
