# 真实 PDF 书籍与工程图纸：三种引擎对比

后续更新：两条活跃分支的嵌套回复导出缺失已修复，见[修复与新基线](pdf-export-replies.md)。下文保留当时的版本、结果及问题记录。

测试日期：2026-10-12。比较当前 Legir 集成实现，版本固定，没有在计时过程中修改业务代码。

当前 PDFium 尚未全面胜出。单文档保存比原方案快，但千页图集打开明显偏慢，整套图集导入不能在测试时限内完成，扫描图重复渲染也有明显短板。MuPDF 在单文档保存和图纸阅读内存方面表现较好，整套图集导入及扫描图局部瓦片同样需要改进。

## 版本、样本与环境

- 原方案：`5c207b2`，PDF.js 6.3.289 + @cantoo/pdf-lib 2.5.3。
- MuPDF：`b6790f0` / `engine/mupdf`，MuPDF 1.28.1。
- PDFium：`e4f3095` / `engine/pdfium`，自编译 PDFium，原生提交 `59ea54cce0179db3269c4c58874249597ca3b118`。WASM 和构建入口哈希见 [provenance.json](pdf-engine-real-corpus/provenance.json)。
- 同一台 Raspberry Pi 5 / Cortex-A76 / 8 GiB RAM，Linux ARM64，Chromium 148.0.7778.167，无头软件渲染，CPU governor 为 ondemand。没有进行本轮 Windows、GPU 加速或 Tauri WebView 测试。

每个样本、每个引擎各运行三轮，共 27 次；每次使用新浏览器，按轮次轮换引擎先后顺序。下面均为三轮中位数，原始每轮数据及范围保留在 [results.json](pdf-engine-real-corpus/results.json) 和 [summary.json](pdf-engine-real-corpus/summary.json)。不把不同文件的成绩合成总分。

## 渲染

单位为毫秒。首张画布列是每轮“打开到 readable + 第一页实际画布完成”的和，再取中位数；不包含 HTML/应用启动、PDF 文件读取和控件模型补全。首次翻页与重复翻页分别取三张抽样页面的中位数，再跨轮取中位数。

画布长边为 1600 像素，放大为 3200；瓦片在页面长边 6400 时绘制 1024×1024 区域。普通画布明确请求 0°，另测 90°旋转瓦片；图集中原本带 Rotate 的页面也采用此共同变换。裁剪坐标保存在原始数据中，不代表 UI 默认页面方向或真实拖动帧率。PNG 任务保留源旋转。画布计时保留生产 worker 的完成/帧回调机制，十几毫秒的差距容易受帧调度影响。

扫描图上，PDFium 重复整页渲染约 1 秒，重复渲染收益较小；原方案的扫描图瓦片明显较快。公开图集上，PDFium 的后续渲染很快，但要先付出约 24 秒的打开时间。

## 导入与导出

单位为秒。保存通过正常 `exportPDF` 修改标题并序列化整个文档，不做图片重压缩。导入包含完整 donor 的预览解析及主 worker 注册；合并保存保留所有原页和 donor 页，并传递导入的控件、批注和链接目标。总计按每轮相加后取中位数，用于比较得到同一个完整合并文件的代价。

- 书籍作为主文档：导入完整 1000 页公开图集，目标 1288 页。
- 公开图集作为主文档：导入完整 288 页书籍，目标 1288 页。
- 扫描图纸作为主文档：导入完整 288 页书籍，目标 331 页。

**涉及公开图集的保存均有下述批注结构差异，不能把相应耗时理解为完全无损导出的成绩。** 书籍本身和扫描图纸的保存通过严格校验。

180 秒是测试脚本的单阶段上限，达到后终止该次浏览器；不是应用主动报错的时间，也不证明操作永远不会完成。两种原生方案各三次在整套图集导入阶段超时，合并保存没有开始，未把这些失败样本从结果中删除。

另一次独立的稀疏协议日志诊断确认 donor 预览已完成，请求已进入主 worker 的 `load(corpus-donor)`。MuPDF 在诊断观察窗内仍未结束；PDFium 诊断返回 `PDF object graft failed (nesting limit exceeded)`。该诊断的行为与正式计时的超时不同，保留 [完整诊断记录](pdf-engine-real-corpus/import-diagnostic.json)，不将诊断耗时替代正式成绩，也不将全部超时归因于一个尚未完全验证的原因。

## 内存

单位为 MiB。使用 Chromium 所有进程的 PSS（含 native/WASM），50 ms 采样；常驻值在主线程及 worker GC 后记录。基线已持有主文档与 donor 的输入字节，因此同时列出绝对值与阅读增量。原方案基线包含其预先创建的空闲 worker。WASM 容量是 arena 容量，不是当前活跃内存。

MuPDF 阅读大图时增量明显较小；扫描图导出/下载时三者的浏览器峰值都约 4.1–4.3 GiB，单一 PDF 实例不等于只有一份输入/输出缓冲。该大文件流程出现了少量浏览器换页和主机 swap 活动，相关计数、温度和负载保留在每次记录中；这些是当前 8 GiB 主机的端到端结果，不是隔离的纯 CPU 排名。

成功完成的原生流程在主 worker 中保有 1 个 PDF 实例，导入复制期间记录到瞬时峰值 2；关闭后该 worker 消失。原方案关闭后仍有两个初始化的空闲 worker。关闭后的浏览器缓存/分配器常驻量不等于泄漏，本轮没有做长期重复开关循环。

## 导出正确性

独立使用 pdf-lib 读取结构、Poppler 提取文字并渲染源文件与输出文件，检查在计时结束后进行。结果见 [validation.json](pdf-engine-real-corpus/validation.json)。

- 48 份文件全部通过页数、全部页尺寸/旋转、编辑后标题、链接目标/URI、表单值检查；本组样本没有可填写表单字段，不能据此推断表单编辑覆盖。
- 255 组抽样页的规范化文字一致，1200 像素长边的 Poppler 渲染逐像素完全一致。每份普通导出抽查源第一页及三张样本页；合并文件追加检查 donor 首、中、末页。这是抽样的独立渲染比较，不是不同引擎的抗锯齿像素必须相同。
- **严格结构检查为 27/48 通过。** 另外 21 份都包含公开图集，均在图集第 217 页少一条 `/Text` 批注列表项，`Text: 3 → 2`、`Popup: 3 → 3`。源文件为 Accepted → Completed → Corrected 的两层回复链，最后一条回复不再列于该页的 Annots；三方案均如此。书籍在前合并时对应第 505 页。抽样画面未见变化，但批注结构不完整。
- 单独检查了书籍与公开图集的实际浏览器画布截图，图文可见。截图存于 `/tmp/legir-three-engine/`，没有将私人图纸页面或完整 PDF 加入仓库。没有对所有页面进行人工检查。

## 当前可定位的改进点

1. PDFium 的 [DocumentSession.inspect](../../src/services/pdfService/engine/documentSession.ts) 对每一页调用 `loadPage` 获取尺寸，[原生桥接](../../packages/pdfium/native/bridge.cpp) 转到 `FPDF_LoadPage`。本地固定版本 PDFium 源码 `fpdfsdk/fpdf_view.cpp:479` 中，该函数调用 `ParseContent`。获取千页尺寸时实际发生了逐页内容解析；尚未独立计时其在 24 秒中所占比例，下一步应先拆出只读取页面几何信息的路径。
2. 大型源文档的对象归并仍有失败路径。PDFium 桥接 `GraftMap::copy` 有 100 层递归限制，诊断已触发；应检查深层对象图及回滚，而非只扩大超时。MuPDF 主 worker 注册路径也需要进一步定位。
3. PDFium 的扫描图重复整页渲染、两种原生方案的扫描图瓦片、导出与下载的大缓冲占用，都是当前测试暴露的优化目标。
4. 三方案共有的深层批注回复保留问题需要独立修复。因为这是版本对比，本次未修改引擎或导出业务实现。
