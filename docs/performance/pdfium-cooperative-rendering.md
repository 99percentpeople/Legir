# PDFium 可暂停渲染与导入、保存优化

2026-10-13。此次优化主要减少后台缩略图占用 worker 导致的等待，以及保存后重复解析和解码。PDFium 的纯栅格化吞吐仍未全面超过 PDF.js；不以“C++ 实现”推断性能优势。所有修改位于 `engine/pdfium`，`main` 仍为 PDF.js + pdf-lib，没有迁移或修改 MuPDF 分支。

## 版本和实际变更

- 原方案：`main` / `engine/pdfjs`，`5e1efc4eee15f4ae7ec5f34b938a77de0ff75b2a`。
- PDFium 基线：`4d6d8d1621d05bb1c8b00669eda48b142d785c06`，已包含前台页面缓存保护。
- 计时 PDFium：`7e1e604d61c540007622cce722f6246c8611f61f`。
- 交付代码：`69958ba31467214fb801adb5355a7f2e20785c6b`。复查补回“没有 AcroForm 时删除最后一个孤立控件”的兼容路径；787 项应用测试重新通过。Corpus 的 `syncFormFields: false` 不进入这条分支，性能记录沿用计时版本，版本不混记。
- 渲染、内存和独立库改动：`a7d431b`；导出无用资源创建修复：`7e1e604`。
- WASM SHA-256：`e277457dd37cb2c33db4ed17d84d4c79904dd1348b2025a5cbd112ad740e2adc`；PDFium 和 Emscripten 版本未变。

具体实现：

1. 显式打开文件时，worker 初始化/WASM 编译与主线程文件读取重叠；书签延迟到需要时读取。
2. 原生渲染改为可继续的任务，默认每约 8 ms 检查一次让出条件。后台预览遇到前台请求会释放本次任务并稍后重试，过期缩放和关闭画布能取消正在运行的渲染。8 ms 是协作预算，页面解析和单个原生操作仍可能超过它。
3. 大图缓存按任务固定生命周期，暂停时不会释放仍被原生渲染器引用的扫描行；图片逐行解码可以让出。默认 256 MiB 上限不变。降低预算时，正在使用的缓存会在任务完成或取消后释放。
4. 导入共享解析器已拥有的不可变编码流存储；加密/新建流仍独立复制，后续写入替换存储。临时源文档关闭后，目标仍可编辑和保存。
5. 标准元数据写入不再触发全局渲染缓存清理；纯元数据/保留原内容的保存不再创建无用字体和空 AcroForm。涉及新对象、表单、共享资源等修改仍保守失效，并非已实现所有编辑的逐页依赖分析。
6. 文件写入和下载避免额外的整份 Uint8Array 复制，保留子视图范围；SharedArrayBuffer 仍转换为普通缓冲区。释放画布时清空其尺寸，预览编码结束也释放绘图缓冲。
7. 独立库增加可选 Canvas display list 原型，见下文；应用默认仍使用原生渐进渲染。

每个文档 worker 保留一个常驻原生 PDF。导入时临时打开 donor，嫁接后销毁；统计中常驻为 1、导入峰值为 2。缓存、导出缓冲和 WASM 容量是不同的内存指标，不能把 worker 数量当成内存占用。

## 相同任务的三轮对比

最终三轮按相同顺序轮换三个版本，27/27 完成。Linux ARM64 Cortex-A76、8 GiB RAM、Chromium 148、软件渲染；构建、自动测试和导出验证均未与计时交叉运行。输入预先加载；同一案例中变换矩阵、页面索引、缩放和裁剪完全相同。完整环境、主机负载/换页记录、峰值和每次响应保留在 [原始记录](pdfium-cooperative-rendering/corpus-results.json) 与 [汇总](pdfium-cooperative-rendering/corpus-summary.json)。三个样本不足以给出强统计显著性，小幅差异应视为波动。

样本为 288 页 Raspberry Pi 书籍、1000 页公开 INDOT 工程图集，以及以前提供的 43 页约 405 MB 扫描图。前者导入整个 INDOT，后两者导入整本书籍。私有图纸和导出的 PDF 留在本机临时目录，不随报告提交。[清单和版本](pdfium-cooperative-rendering/manifest.json)。

所有耗时为 ms；完整页面长边 1600 px，放大页长边 3200 px，瓦片为长边 6400 px 页面上的四个 1024×1024 区域。抽样页与单块瓦片先在每轮取中位数，再取三轮中位数；四块累计是每轮四次请求响应耗时之和，排除请求之间的测试采样等待，并非显示器出画延迟。分项相加不一定等于每轮总量的中位数。

## 内存

单位 MiB，均为浏览器所有相关进程的 PSS 峰值中位数，50 ms 采样，可能漏掉更短峰值。包括 JS、WASM、Canvas、浏览器进程和预载入的输入数据；不是 JS heap。WASM capacity 是容量高水位，释放对象不保证它缩小。关闭后原始预载入输入也被释放，因此相对基线的差值可能为负。

| 处理峰值，不含下载阶段 | 原方案 | PDFium 基线 | 最终 PDFium |
| ---------------------- | -----: | ----------: | ----------: |
| 书籍＋图集导入/合并    | 2284.5 |      2256.6 |      2020.4 |
| 图集＋书籍导入/合并    | 2125.0 |      2299.5 |      2257.6 |
| 扫描图＋书籍导入/合并  | 3800.1 |      3535.0 |      3536.8 |

书籍工作流约减少 236 MiB（10.5%）；图集约减少 42 MiB；扫描图基本持平，不能宣称普遍降低内存。书籍工作流的 WASM 容量从约 1096 降到 863 MiB，扫描图仍约 1509 MiB。

Corpus 为保证一致，下载阶段仍使用共同 harness 的 `output.slice()`→Blob，而非最终应用的下载函数。因此此处不把应用取消额外下载复制的收益混入对比。包括该共同下载阶段的峰值如下；其内存不代表最终应用保存路径的精确峰值。

## 完整性、功能和可行性检查

- 99 个应用测试文件、787 项测试通过；独立 PDFium 库 32 项测试通过。涵盖暂停/恢复/取消、缓存固定与预算缩小、捐赠文档关闭后的流独立性、加密导入/保存、元数据保存不创建空表单，以及取消/失败时资源释放。
- lint、应用与 www 类型检查、Web 生产构建、Tauri 前端构建通过。没有把前端构建当成 Windows/Tauri 实机验证。
- 渐进渲染的 42 组原生 RGBA 哈希与先前同步渲染完全一致，包含整页、重复绘制、旋转、裁剪瓦片及缓存淘汰后重访。[记录](pdfium-cooperative-rendering/native-pixels.json)。
- 54/54 份导出经独立 pdf-lib 和 Poppler 检查通过：所有页的数量、尺寸、旋转、批注类型/回复关系/状态、链接目标及表单值；另检查修改后的标题、抽样页文字和栅格图像。像素阈值为通道差超过 16 的像素不足 0.1%，这不是每一页的像素逐个相等证明。[验证](pdfium-cooperative-rendering/export-validation.json)。
- 最终生产 PWA 离线完成表单编辑、插页、撤销重做、导入、保存和重新读取：8 页、3 个字段、编辑值正确；活动 worker 为 1，关闭后为 0。没有页面 JS 异常或检查时可见坏图。仍有一次旧版已记录的被撤销 Blob 缩略图 `ERR_FILE_NOT_FOUND`，不声称所有资源请求成功。[记录](pdfium-cooperative-rendering/ui-smoke.json)、[截图](pdfium-cooperative-rendering/ui.png)。
- Canvas 原型支持不透明 RGB/灰度路径和不含额外色彩/方向信息的 JPEG，使用 PDFium 已解析的对象，浏览器执行实际绘制。路径/JPEG 的整页、旋转、瓦片和取消验证通过；不同抗锯齿/缩放产生少量像素差异。真实三个文件共 9 个抽样页均因复杂特性返回不支持，应整页回退原生渲染。它没有进入默认应用路径，也没有验证为通用更快的渲染器。[原型记录](pdfium-cooperative-rendering/canvas-plan.json)、[库接口](../../packages/pdfium/README.md#cooperative-and-experimental-canvas-rendering)。

复现入口为 `scripts/pdf-benchmark/{corpus,corpus-validate,reader-ui,preemption,native-render,canvas-plan,ui}.mjs`，详见 [脚本说明](../../scripts/pdf-benchmark/README.md)。导出文件、构建副本和完整运行日志保留在 `/tmp/legir-pdfium-next/`。本机是 CPU 软件渲染环境，结果不代表用户 Windows 显卡、Tauri WebView 或所有 PDF；尤其不支持“PDFium 已全面超过原实现”的结论。
