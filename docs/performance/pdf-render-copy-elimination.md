# MuPDF 像素复制优化与复测

测试日期：2026-10-12。基线为上一轮已经完成单实例迁移的 MuPDF 版本；原 PDF.js 版本仅作独立参照。修改在本地工作区，Web 和 Tauri 共用前端均覆盖。本次运行测试仍是 Raspberry Pi 5 / Linux ARM64 / Chromium 148.0.7778.167，没有用 Tauri 原生 WebView 或用户真实大图纸作性能证明。

## 改动

页面、瓦片、缩略图和批注预览现在通过 `drawPageToCanvas`，在原生 Pixmap 存活期间把其像素视图同步写入 Canvas，随后释放 Pixmap。原路径中的整页 `new Uint8ClampedArray(pixmap.getPixels())` 复制已移除。常驻 PDF 仍为每文档一个 Worker 中的一个 MuPDF 实例。

借用像素期间没有 `await` 或新的原生分配；透明图层在自己的临时 Pixmap 中转为非预乘 alpha。需要保留或传输像素的 `rasterizePage` 接口继续返回独立副本。画布尺寸只在光栅化成功后更新，渲染失败保留旧画布；原生设备和 Pixmap 在写入失败时也会释放。没有降低图像采样或字体抗锯齿质量，也没有增加页面位图缓存或第二个常驻 PDF。

相关实现：[raster.ts](../../src/services/pdfService/engine/raster.ts)、[Worker](../../src/workers/pdf-render.worker.ts)。接口依据：[MuPDF Pixmap](https://mupdf.readthedocs.io/en/1.28.1/reference/javascript/types/Pixmap.html)、[ImageData](https://developer.mozilla.org/en-US/docs/Web/API/ImageData/ImageData)；借用内存的具体行为同时核对了项目固定的 MuPDF 1.28.1 JS 绑定。

## 方法与边界

固定样本与上轮相同：12 页表单文档、60 页/45.07 MiB 图片文档，以及 4 页导入文档。图片是高频随机噪声，不代表所有扫描件或工程图。[源码、Worker 构建与样本哈希](pdf-render-copy-elimination/provenance.json)记录了对照版本。

渲染对比使用 [历史 render.mjs（取回说明）](../../scripts/pdf-benchmark/ARCHIVE.md)：三个变体、两个样本、四种渲染路径、三轮，轮间反转变体顺序。每组使用两次预热和八次测量，共 72 组、720 次渲染（其中 576 次计入统计），每个变体/样本使用新浏览器。表格是三个“每轮八次中位数”的中位数，范围和逐次结果全部保留。计时期间没有同时运行本任务的构建、测试或其他浏览器验证。

Canvas 使用真正从 DOM 转交 Worker 的 OffscreenCanvas。150% 为 900 × 1200，300% 为 1800 × 2400；旋转瓦片为页面 300%/90° 下偏移 (120,160) 的 640 × 480 区域。PNG 路径包含编码和传输；Canvas 路径包含请求/回执及既有的动画帧等待。画面读回和哈希发生在整组计时之后，避免读回改变浏览器绘制后端。

同时用浏览器内的函数包装记录分段耗时，不修改生产代码的渲染行为。`beforePresentation` 指 Worker 收到渲染请求，到其调用 `requestAnimationFrame` 之间的时间；不含等帧和响应。**这不是实际屏幕显示延迟**，也不是 GPU 执行时间。PDF.js 的 Canvas 指令提交和 MuPDF 的同步光栅化路径不同，不能把两者的此项分段值直接当成引擎 CPU 性能比较。三轮样本较少，不作统计显著性结论。

## 渲染结果

单位 ms；正百分比表示耗时增加。这里的总耗时保留实际等帧和 Worker 消息开销。

| 样本 / 路径             | 原 PDF.js | 优化前 MuPDF | 优化后 MuPDF | 优化后相对优化前 |
| ----------------------- | --------: | -----------: | -----------: | ---------------: |
| 表单页 / PNG，150%      |      27.7 |         30.9 |         27.1 |           -12.3% |
| 表单页 / Canvas，150%   |      12.2 |          9.3 |          9.3 |            -0.5% |
| 表单页 / Canvas，300%   |      22.3 |         23.5 |         18.6 |           -20.9% |
| 表单页 / 旋转瓦片，300% |      12.1 |         12.6 |         12.1 |            -4.4% |
| 图片页 / PNG，150%      |      32.9 |         62.0 |         64.1 |            +3.4% |
| 图片页 / Canvas，150%   |      12.2 |         17.1 |         15.5 |            -9.4% |
| 图片页 / Canvas，300%   |      27.6 |         24.4 |         16.9 |           -30.8% |
| 图片页 / 旋转瓦片，300% |      12.5 |         12.0 |         12.5 |            +3.8% |

最明确的总耗时收益在 300% 画布：图片页 24.4 → 16.9 ms（约减少 31%），表单页 23.5 → 18.6 ms（约减少 21%）。150% 图片页小幅改善；普通表单页和瓦片的总响应更多受等帧与调度影响，没有一致的同比例收益。

大图 PNG 总耗时为 62.0 → 64.1 ms，本轮略增，不能宣称此路径提速。其 PNG 编码分段为 38.6 → 39.9 ms、Blob 取字节为 5.2 → 6.0 ms；移除约 1.7 ms 的像素复制没有转换成总耗时下降。本次未修改编码路径，这仍是后续需要单独分析的部分。

同为 MuPDF 的前后对比中，Worker 到请求下一帧之前的耗时如下，单位 ms：

| 样本 / Canvas 路径 | 优化前 | 优化后 |
| ------------------ | -----: | -----: |
| 表单页 / 150%      |   5.70 |   3.70 |
| 表单页 / 300%      |  17.20 |  10.60 |
| 表单页 / 旋转瓦片  |   2.00 |   1.70 |
| 图片页 / 150%      |  15.55 |  14.05 |
| 图片页 / 300%      |  19.75 |  12.85 |
| 图片页 / 旋转瓦片  |   1.70 |   1.20 |

浏览器插桩确认每次中间 RGBA 数组的复制量：150% 整页从 4,320,000 字节降为 0；300% 整页从 17,280,000 字节（16.48 MiB）降为 0；瓦片从 1,228,800 字节降为 0。这仅指移除的临时数组；MuPDF 的光栅缓冲、Canvas 自己的像素存储和必要的 Canvas 写入仍存在。

24 组优化前后画面（两种样本 × 四种路径 × 三轮）的像素 SHA-256 全部相同。原 PDF.js 的像素不作为等价判定标准，因为其采样结果与 MuPDF 本来就不同。[原始渲染记录](pdf-render-copy-elimination/render.json)、[三轮汇总](pdf-render-copy-elimination/render-summary.json)。

## 导入导出及内存复测

沿用原来的管线基准，优化前后各三个场景、各三轮，共 18 次新浏览器测试。它每个阶段包含内存采样和 GC，与上面的连续热渲染基准不同，不把两组数字混用。每次导出均由独立读取器重开：修改值、合并后页数/表单数分别为 16/6、64/22、72/24，全部通过；原生 PDF 常驻数为 1，临时 donor 导入峰值为 2。

| 场景 / 耗时，ms                 | 优化前 | 优化后 |
| ------------------------------- | -----: | -----: |
| 12 页小文档 / 导出              |   69.0 |   65.2 |
| 12 页小文档 / 导入              |  418.5 |  403.6 |
| 12 页小文档 / 合并导出          |   51.1 |   46.9 |
| 60 页大文档 / 导出              |  176.1 |  177.9 |
| 60 页大文档 / 导入              |  405.8 |  396.4 |
| 60 页大文档 / 合并导出          |  143.8 |  166.4 |
| 小文档导入整个大文档 / 导出     |   63.6 |   73.3 |
| 小文档导入整个大文档 / 导入     |  653.3 |  665.7 |
| 小文档导入整个大文档 / 合并导出 |  340.0 |  344.2 |

导入导出功能检查通过，但耗时有波动，例如大文档合并导出 143.8 → 166.4 ms。本轮只改渲染输出路径，没有依据宣称导入导出提速或保证其性能无回归；全部阶段和 min/max 保留在 [管线汇总](pdf-render-copy-elimination/pipeline-summary.json)。

内存为 Chromium 进程集合的总 PSS，不是 PDF 独占内存。每 50 ms 采样峰值；保留值在显式 GC 后读取，关闭后等待下载 URL 回收。大文档解析后保留量约 540 MiB，前后基本相同。本次改善主要是瞬时分配量，不是大幅降低常驻内存。

## 功能验证与复现

- 全量 Vitest：96 个文件、765 项测试通过。
- 新测试核对借用内存的生命周期、透明度、裁剪旋转、原生渲染失败后旧画布保留，以及写入失败后的资源释放与再次渲染。
- `bun run lint` 通过，包括 ESLint、应用和网站 TypeScript 检查。
- `bun run build` 与 Tauri 模式前端构建通过；没有运行 Tauri 原生安装包。
- 生产 PWA 离线测试通过：文本层/画布、表单 Alice → Bob、缩略图更新、空白页、撤销/重做、导入及保存。独立重开下载文件为 8 页、3 个字段；可见破图 0，编辑时 Worker 1、关闭后 0，`pageerror` 为空。[UI 结果](pdf-render-copy-elimination/ui.json)
- UI 仍有上轮相同的一条 `net::ERR_FILE_NOT_FOUND` 资源警告；管线基准有 HTTP 404 控制台警告。没有可见破图或未处理脚本错误，不把它们描述成“控制台无错误”。
