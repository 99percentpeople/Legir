# PDFium Canvas 指令与 OffscreenCanvas 可行性测试

2026-10-13，基于 `engine/pdfium` 的 `cc817a0`，原生 WASM 未修改。

**结论：扫描图像页面有提速空间；OffscreenCanvas 本身已经在用。当前实验不能直接替换完整渲染器。** 缓存浏览器解码的图像可以改善整页绘制，但高质量缩放的分块成本、图像保真度、内存预算和复杂 PDF 支持仍需处理。

## 当前链路和实验范围

正文画布通过 `transferControlToOffscreen()` 交给现有 PDF Worker。当前链路是 PDFium 解析和光栅化 → 借用 WASM RGBA 视图 → `putImageData` → 转移画布；没有额外的 JS 整页像素副本。实验链路是同一个 Worker、同一个 PDFium 文档 → 已解析对象的指令和 JPEG 数据 → 浏览器 Canvas 2D 绘制。显示列表和图像缓存不是第二个 PDF 文档。

测试包含三种路径：

- `native`：与应用相同的 8 ms 协作式 PDFium 渲染，写入 OffscreenCanvas。
- `commands`：现有 `createCanvasPlan` / `drawCanvasPlan` 实验 API；每次执行都会解码 JPEG。
- `cached`：只存在于测试脚本中的 Path2D、ImageBitmap 缓存与保守的可见范围裁剪，使用 MessageChannel 让出执行权。

发现最近邻缩小导致质量问题后，另测 `cached-high`：缓存同样的图像，缩小时启用平滑并设置 `imageSmoothingQuality = "high"`。它尚未实现 PDF.js 的分级缩小，也没有进入默认应用路径。实验均保留一次离屏暂存绘制后发布整帧的流程。

## 真实图纸结果

405,260,653 字节、43 页扫描工程图纸，抽样第 2、22、43 页。三页的普通缓存回放都能运行，但画质不合格，因此下面优先列出第 22 页追加的高质量实验。每个模式每轮启动独立 Chromium、Worker 和一个 PDF 文档，交替测试顺序，共三轮。

以下为每轮四次热绘制中位数的三轮中位数，单位 ms；首次绘制单独计入载入页、生成指令、解码及绘制，**不含 WASM 启动、文件读取和文档构造**。这些是绘制调用及协作让出时间，不是物理屏幕显示时间。

| 第 22 页任务                | PDFium 原生 | Canvas 缓存＋高质量缩放 |            变化 |
| --------------------------- | ----------: | ----------------------: | --------------: |
| 首次页面绘制，含准备        |      1193.3 |                   670.3 |  耗时减少 43.8% |
| 1600 px 长边整页重复绘制    |       255.9 |                    91.2 |  耗时减少 64.4% |
| 3200 px 长边整页重复绘制    |       432.3 |                   370.2 |  耗时减少 14.4% |
| 6400 px 长边下的 1024² 分块 |        22.3 |                    55.0 | 耗时增加 146.6% |

包含 Worker 动画帧确认后的响应时间，对应后三行是 258.0→96.5、438.5→391.6、29.8→58.6 ms，同样不能当作屏幕扫描输出时间。

原生 `putImageData` 写入在上述三个尺寸分别约 1.4、5.1、0.8 ms。1600 px 绘制的绝大多数时间仍在原生光栅化/采样中，单纯省掉像素写入不足以解释或解决瓶颈。

## 为什么不能直接使用最快的数字

第 22 页的普通 `cached` 热绘制只需约 9.8、28.6、4.4 ms，但当前指令原型把 PDF 的插值标志直接赋给 `imageSmoothingEnabled`。该扫描图没有启用插值，缩小图像时变成最近邻采样，细线和文字出现明显锯齿、断裂。此组数据不能作为保持画质的性能收益。

独立于计时的像素验证，统计与同尺寸 PDFium 输出相比，任一通道差大于 16 的像素比例：

| 第 22 页     | 普通缓存 Canvas | 高质量缩放 Canvas |
| ------------ | --------------: | ----------------: |
| 1600 px 整页 |          15.33% |             8.03% |
| 3200 px 整页 |          11.09% |             7.08% |
| 1024² 分块   |          17.79% |            11.79% |

1600 px 整页的平均通道绝对误差由 8.25 降至 2.93（0–255 范围）。查看实际整页 PNG 后，高质量版消除了普通缓存版明显的最近邻断线问题；这仍不是与 PDFium 像素一致或所有细节等价的证明。没有将任何一组标记为通过生产画质验收。用户图纸及其截图仅留在本机临时目录，没有放进仓库。

缓存版与现有 SDK 指令回放在所有已测合成/真实页面尺寸上的像素逐个相等，说明缓存和裁剪没有引入额外差异；主要问题已经存在于原型的绘制语义中。

## 复杂路径和真实页面覆盖率

1 万条短曲线的合成页面，1600 px 长边热绘制：原生 69.0 ms，现有指令回放 180.3 ms，缓存 Path2D 加裁剪后 115.1 ms。1024² 分块分别约 9.3、149.0、21.9 ms。该软件渲染环境下，导出路径并逐条调用 Canvas 没有超过原生 PDFium，不能从扫描图像的结果推断矢量工程图也会提速。

本次按应用正文使用的 `annotations: false` 检查原性能语料的抽样页：

| 文件               | 抽样页（从 1 开始） | 正文指令支持 |
| ------------------ | ------------------- | ------------ |
| 288 页书籍         | 15、144、288        | 0/3          |
| 1000 页 INDOT 图集 | 217、500、1000      | 0/3          |
| 43 页扫描图纸      | 2、22、43           | 3/3          |

书籍资源中存在字体、ICC/CMYK 图像、蒙版和透明组；INDOT 图集存在字体、图形状态和 Form。资源清单用于定位后续支持范围，不等同于逐对象拒绝原因跟踪。原型源代码明确拒绝文本、Form、裁剪、扩展图形状态等情况。

之前 `canvas-plan.mjs` 使用 `createCanvasPlan(page)` 默认选项，包含批注时扫描页也被拒绝。本次三个扫描抽样页均确认“正文支持、包含批注不支持”。因此旧报告中的全部回退结论只适用于当时的选项和抽样页；不能据此认为扫描正文一定无法走 Canvas。完整批注/表单外观仍需现有绘制层或原生回退，不能为了使用 Canvas 而丢弃。

## 内存与下一步

第 22 页的浏览器解码图像按 RGBA 计算约 **238.1 MiB**，指令导出还持有约 9 MiB 编码 JPEG。原生超大图像缓存约 178.6 MiB。实验中的 WASM 容量从约 719.9 降至 467.3 MiB，但 ImageBitmap 的内存在 WASM 外，**不能据此宣称总内存下降**；本实验没有测进程 PSS 峰值。

建议先实现扫描页专用后端，按顺序处理：

1. 参照本地 PDF.js `getImageSmoothingEnabled`、`_scaleImage` 的缩放策略，建立有预算的分辨率分级缓存；同页滚动/缩放复用解码结果，避免每个分块重新解码整张图像。
2. 解决分块高质量采样成本，在收益和保真度验证前保留原生分块路径。页面、图像和显示列表的缓存必须统一记账，关闭文件和编辑失效时释放 ImageBitmap。
3. 补齐安全的页面能力判断、取消和编辑后的失效逻辑，再验证批注、表单、旋转、裁剪和色彩一致性。保持一个 Worker 中一个 PDFium 文档。
4. 文字、Form、透明组、复杂裁剪等完整 Canvas 后端单独评估；本轮数据不支持立即全面迁移，也不能证明它会比 PDF.js 全面更快。

这是基于当前源码和实测的实施建议，尚未应用到默认渲染器。

## 环境、验证和复现

Linux ARM64 Cortex-A76、Chromium 148；`--disable-gpu`，浏览器报告 2D Canvas 和光栅化使用软件路径。没有做 Windows GPU、Tauri WebView 或其他浏览器测试，不能将这些结果当作对应设备的性能承诺。[OffscreenCanvas 官方说明](https://developer.mozilla.org/en-US/docs/Web/API/OffscreenCanvas)说明它可将绘制放到 Worker；硬件加速和上下文选项仍由浏览器环境决定。避免在计时中执行画布读回；`willReadFrequently` 会偏向软件 Canvas，见[上下文选项](https://developer.mozilla.org/en-US/docs/Web/API/OffscreenCanvas/getContext)。

合成组 18、真实扫描组 27、高质量补充组 6，共 51 个独立计时会话完成；另做 9 个真实页面覆盖率会话和独立像素验证。每个会话只持有一个 PDF 文档，计时会话及后续真实/高质量验证均断言关闭后原生文档/超大图像缓存归零。初版合成像素验证执行关闭但未保存关闭统计。原型 ImageBitmap 通过显式 `close()` 释放；不能将资源引用检查当作操作系统已归还全部内存的证明。

测试期间没有并行运行构建、其他性能测试或验证程序。没有变更应用渲染代码或原生库；新增手动测试脚本通过 ESLint 和语法检查。没有为这次纯实验重新运行应用完整测试。
