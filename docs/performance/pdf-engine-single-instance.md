# PDF 单实例迁移与性能对比

测试日期：2026-10-12。修改覆盖 Web 和 Tauri 共用前端；这里的运行结果来自 Linux Chromium，未验证 Tauri 原生 WebView。

每个打开的编辑文档现在由一个常驻 `pdf-render.worker` 和一个原生 MuPDF `PDFDocument` 负责渲染、解析、批注/表单处理、导出、文本提取及 OCR 图片准备。主线程保留编辑模型和源字节，不再解析另一份 PDF 对象图。导入时临时打开 donor，graft 到同一文档后销毁，所以这里的“单实例”指常驻实例；导入峰值为两个。导入预览作为独立打开的文档，关闭预览时释放自己的 Worker。

`@cantoo/pdf-lib` 2.5.3 仍提供布局、字体和表单外观工具。适配器在同一 MuPDF xref 上提供惰性视图，没有第二份已解析 xref/流对象图。文件解析及最终序列化使用 MuPDF 1.28.1。导出和缩略图在原生 journal 事务中执行，完成、失败或取消后恢复源状态。详情见 [架构说明](../ARCHITECTURE.md#pdf-pipeline)。

## 对照版本和方法

- 原 PDF.js 版本：`5c207b231c19ac23b8db7aebfa7c374a2bcaf7c3`，PDF.js 6.3.289 + pdf-lib 2.5.3。
- 上轮 MuPDF 桥接版：本轮开始前的未提交源码快照，仍有主线程编辑对象图和临时内容 Worker；使用 MuPDF 1.28.1。
- 单实例版：本轮未提交工作区，包含常驻实例、惰性全局 Worker 和关闭后不重建 Worker 的修复。[来源、源码和构建产物哈希](pdf-engine-single-instance/provenance.json)记录了可核对的版本信息。

主机为 Raspberry Pi 5 / 8 GB / Linux ARM64；Chromium 148.0.7778.167。三个版本使用同一个基准入口，分别按各自 Vite/Worker 配置构建。三个场景各跑三轮，每轮重新启动浏览器，共 27 轮。变体顺序执行，计时期间没有同时运行构建、测试或其他本任务浏览器。下表为三轮中位数，所有最小/最大值见 [汇总 JSON](pdf-engine-single-instance/summary.json)。只有三轮，结果用于本机比较，不构成统计显著性或桌面实机性能证明。

样本固定随机种子和日期：小文档为 12 页、4 个表单域、30,324 字节；大文档为 60 页、20 个表单域、47,260,228 字节（45.07 MiB），每页包含不同的 512 × 512 RGB 噪声图片；小导入文档为 4 页、2 个表单域、11,188 字节。[样本哈希](pdf-engine-single-instance/fixtures.json)可用于复现。没有使用用户真实大文件或敏感文件。

先等待可读、渲染，再解析编辑模型。渲染固定为 1.5 倍的 900 × 1200 PNG，计时包含 Worker 渲染和 PNG 编码，不包含随后校验图片像素的时间。导入计时包括预览解析和向主文档注册源。导出后用独立 pdf-lib 读取器重开文件检查页数、表单和修改值。测的是 PDF 管线，未测 UI 滚动/缩放、文件选择器或桌面保存对话框。

## 内存

以下为 Chromium 报告的进程集合在 `/proc/<pid>/smaps_rollup` 中的 PSS 总和，包含浏览器、渲染器、Worker、原生/WASM 内存，**不是 PDF 独占内存**。RSS 同时保留在原始 JSON 中。PSS 按比例分摊共享页，避免像 RSS 求和那样把共享页重复全额计数。

每 50 ms 采样一次峰值，可能漏掉更短的尖峰。保留值在主线程和 Worker 显式 GC 后等待 150 ms 测得；关闭后额外等待 1.2 s，让下载 Blob URL 被撤销。基线已载入测试模块和两份输入字节；不同实现的模块、Worker 初始化时机不同，因此同时列出绝对值和每轮自身基线增量。渲染阶段的内存采样也包含 PNG 解码、画布及像素哈希验证的开销，三版使用相同验证流程。

大文档解析后的总 PSS 从桥接版 619.6 MiB 降到 539.0 MiB，全流程采样峰值从 1035.4 MiB 降到 796.5 MiB。原 PDF.js 的峰值为 809.9 MiB，与单实例版接近；单实例版相对自身基线的峰值增量却更高，不能据此宣称所有阶段的 PDF 内存都下降。

导入大文档仍是薄弱点：单实例版峰值 829.0 MiB，高于原 PDF.js 的 780.6 MiB；合并导出后保留 755.7 MiB，也高于原版 698.5 MiB 和桥接版 685.9 MiB。graft 与 journal/分配器可以保留已释放对象的存储，直到 Worker 关闭。源回收会删掉页面和对象，但不保证立即归还其物理内存。后续若要优化这一场景，需要单独分析 graft、撤销日志和导出时对象复制，不能只用“实例数减少”推断内存收益。

九轮单实例测量均报告常驻原生文档数 1、导入时峰值 2、源数 2。WASM arena 容量小文档约 22 MiB、大文档约 128.4 MiB、导入大文档约 223.5 MiB；容量是预留空间，不等同于存活对象大小或 PSS。生产 UI 测试确认关闭后 Worker 数为 0。

## 功能与图像核对

- 每轮导出均保留修改后的文本域值 `BENCHMARK EDIT`。合并后的页数/表单数分别为 16/6、64/22、72/24，九轮单实例均通过独立重开检查。
- 当前版与上轮 MuPDF 的首次、重复和末页渲染共 27 个像素哈希全部一致。单独截图比较中，两份首屏样本的像素差为 0。
- 与原 PDF.js 并非逐像素相同：RGB 任一通道差值大于 8 的像素占比，小文档为 4.62%，噪声图片页为 54.63%；平均 RGB 绝对差为 2.14/255 和 19.37/255。小文档人工查看未见布局/字段位置变化；高频噪声会放大采样差异。这些结果不代表所有字体、扫描件和工程图的视觉兼容性。[像素对比数据](pdf-engine-single-instance/visual-comparison.json)
- 生产 PWA 安装后切换离线，验证文本提取/画布显示、表单 Alice → Bob、缩略图更新、插入空白页、撤销/重做、导入及保存。下载文件独立重开为 8 页、3 个表单域，修改值和导入字段保留。可见破图数 0，编辑时 Worker 数 1，关闭后为 0，整个流程未捕获 `pageerror`。[UI 结果](pdf-engine-single-instance/ui.json)
- UI 仍记录一次 `net::ERR_FILE_NOT_FOUND` 控制台资源警告；最终没有可见破图。本次没有进一步确认该资源的来源。管线基准也各有一条 HTTP 404 控制台警告，原始记录完整保留，不把这些运行描述成“控制台零错误”。
- 自动测试覆盖原生对象视图、事务恢复/取消、加密权限、表单/批注、页面结构导入导出、源释放、Worker 归属与关闭。最终全量测试、lint 和构建结果见下文。

OCR 目前提供同一文档实例上的页面图片/文字准备，模型识别调用按后续模型接入方案实现，本次没有声称完成 OCR 识别。
